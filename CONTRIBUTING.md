# Contributing to SENTRY

This file covers cross-repo contribution rules. Repo-specific conventions (the FastAPI module checklist, the dashboard feature-folder shape) live in each repo's README and, on the API side, in `Api/CLAUDE.md`.

---

## Which repo owns what

| Concern | Repo | Notes |
|---|---|---|
| Database schema, migrations, ORM models | `Api/` | Alembic is the source of truth — migrations are autogenerated from `BaseModel` subclasses. Never write to PG from anywhere else |
| Inference pipeline (Stages 1–4), Groq/Gemini clients, scrapers | `Api/` | All long-running work runs as `asyncio` background tasks on the API process |
| Auth (JWT for users, install tokens for extensions) | `Api/` | Both surfaces are token-issuing endpoints; the dashboard only consumes them |
| Rate limits, blocklist/allowlist enforcement | `Api/` | slowapi for the extension surface, env-driven allow/block lists at register time |
| API contract — endpoints, payloads, error envelope, status codes | `Api/` | Owned by the API; the dashboard mirrors it. Breaking changes need a coordinated PR |
| Dashboard UI, charts, filters, navigation | `dashboard/` | |
| Cookie storage of tokens, silent refresh queueing, `/login` redirect | `dashboard/` | The API does not mandate cookie storage — it just issues tokens |
| TypeScript types that mirror the wire format | `dashboard/` | `src/features/*/api/*.types.ts` and `src/lib/api-core/types.ts`. The API does not generate these; they are hand-mirrored |

If a feature touches both repos, the API change merges first and the dashboard PR pins to the API change in its description.

---

## Branch strategy

- Trunk-based: branch from `main`, PR back into `main`. Long-lived branches are discouraged.
- Branch naming: `feat/<short-description>`, `fix/<short-description>`, `chore/<short-description>`.
- Each PR is scoped to one repo. If a feature spans both, open two PRs and link them in the descriptions.
- Squash on merge. Keep the commit message imperative and reference the linked PR if one exists.

## Working across both repos

The shared boundary is the HTTP API. When a change crosses the boundary, follow this order:

1. **Define the contract first.** If you are adding or changing an endpoint, sketch the request and response DTOs as a comment on the issue or in the PR description before writing code. Pin field casing (camelCase on the wire), required vs optional fields, and the error codes the dashboard should surface differently.
2. **Land the API change.** Add the route, the DTO, the migration if one is needed, and a sample `curl` in the PR description. Include the dashboard PR link if one is in flight.
3. **Land the dashboard change.** Update the matching `*.types.ts`, the `*.api.ts` call, the TanStack Query hook, and any UI. Include the API PR link.

**Do not** ship a dashboard change that depends on an unmerged API change to staging — the dashboard's TypeScript will not catch a missing field at the wire level (no codegen), so the bug only surfaces at runtime.

## Testing changes that affect both sides

Neither repo has an automated test suite right now. Until one is added, manual verification is mandatory for cross-repo changes:

1. Boot the API locally with `python main.py` and the dashboard with `npm run dev`.
2. Sign in as the seeded admin (see [README.md → Local development](./README.md#local-development-guide)).
3. Exercise the changed flow end-to-end:
   - **For an inference change**: submit an email through `/inference?tab=submit`, watch the detail tab transition `pipeline_status` from `running` → `complete`, confirm the new field renders.
   - **For an auth change**: sign out, sign back in, leave the tab idle past `ACCESS_TOKEN_EXPIRE_MINUTES`, then click a protected route and confirm silent refresh replays the request without an interactive re-login.
   - **For an install-management change**: the easiest mirror of the extension is `curl` against `/api/v1/auth/extension/register` (sending a stub `X-Google-Access-Token`) and `/api/v1/emails/analyze`. Confirm the install appears in the dashboard's `/extension/installs` list.
4. Check the API logs (`logs/app.log`) for warnings or unexpected stack traces.
5. For changes that touch the response envelope or DTO shape, open the dashboard's network tab and confirm the wire payload matches what the TypeScript expects.

If the change touches the inference pipeline:
- Verify the early-exit rule still fires when Stage 1 confidence ≥ `EARLY_EXIT_CONFIDENCE`.
- Verify long-running pipelines drain on shutdown (`Ctrl+C` the API and look for the `Draining N in-flight pipeline task(s)` log line).

## API contract conventions

These conventions are enforced by the API and assumed by the dashboard. Violating them breaks the dashboard silently — **review every PR against this list**.

### Response envelope

Every successful response is `ApiResponse.ok(value=..., message=...)`:

```json
{ "success": true, "message": "...", "value": <T> }
```

Paginated lists are `PaginatedResponse.ok(value=[...], page=, total=, page_size=)`:

```json
{ "success": true, "value": [<T>, ...], "pagination": { "page": 1, "pageSize": 20, "total": 137, "totalPages": 7 } }
```

`value` and `error` are mutually exclusive (validator-enforced on the API side). The dashboard's axios interceptor unwraps `value` for you — endpoints **must** put their payload there.

### Error envelope

Errors raise an `AppException` subclass; the global handler returns:

```json
{ "success": false, "message": "...", "error": { "title": "...", "code": "...", "status": 400, "details": [...], "fieldErrors": {"<field>": [...]} } }
```

Use the existing exception classes (`NotFoundException`, `ConflictException`, `BadRequestException`, `AuthenticationException`, `AuthorizationException`, `ValidationException`, `ServiceUnavailableException`). Use `ErrorDetail.builder(...).add_field_error(...)` when the dashboard needs to highlight specific form fields. Use direct `ErrorDetail(...)` otherwise.

The dashboard reacts to specific codes:
- `AUTH_FAILED` (401) → silent refresh attempt
- `NOT_WHITELISTED` (403, extension only) → render the "not authorised" badge
- `RATE_LIMITED` (429) → toast + back-off
- `NETWORK_ERROR` (status 0, dashboard-synthesised) → connection toast

### Casing — camelCase on the wire

Response DTOs declare camelCase aliases (`Field(alias="createdAt")`) and `Config: populate_by_name = True; from_attributes = True`. The `from_{entity}(entity)` static factory passes values **by alias name**. Serialisation uses `model_dump(exclude_none=True, by_alias=True)`.

Request DTOs accept camelCase via the same alias config. The one historical exception is `POST /auth/refresh`, which accepts snake_case `refresh_token` for backward compatibility — the dashboard sends snake_case explicitly on this one route. Do not introduce new snake_case request fields.

### Routing & method semantics

- All routes live under `/api/v1`. The router prefix is set in `src/core/factory.py::_register_routers`.
- `POST` for creation and idempotent state transitions; `PATCH` for partial updates; `DELETE` for removal. `GET` must be side-effect-free.
- `202 Accepted` for endpoints that schedule background work (`POST /inference/emails`, `/inference/emails/batch`, `/inference/emails/{id}/reanalyze`).
- Route-order gotcha: literal segments like `/domains/blacklist` **must** be declared before `/{install_id}` UUID routes, or FastAPI will try to parse the literal as a UUID (`422`).

### Dependencies & guards

- Dashboard endpoints use `Depends(require_authenticated)` (any role) or `Depends(require_admin)`. Apply at the router level for whole-router guards, at the route level for one-off elevation.
- Extension endpoints use `Depends(require_install)` — never `get_current_user`. The two surfaces share no state.
- `require_install` exposes `request.state.install_token_hash` for downstream rate limiting (`install_token_key`) and renewal — preserve this when refactoring.

### Background work

- Schedule with `pipeline_runner.spawn(...)` (it retains a strong task reference and removes it on completion). Never call `asyncio.create_task(...)` for pipeline work directly.
- New long-running loops go in `src/core/lifespan.py`: create the task before `yield`, cancel + `await` with `CancelledError` suppression after `yield`. The loop body must catch `CancelledError` and re-raise.

### Config & env

- New env vars are declared in `src/configs/application.yaml` with the pipe format (`"${ENV_VAR:default} | type"`) and a matching entry in `.env.example`. The IDE stub regenerates itself.
- Required keys cause startup to abort if unset. Use this sparingly — it is appropriate for `DATABASE_URL`, `JWT_SECRET_KEY`, `ADMIN_PASSWORD`, `GROQ_API_KEY`, `GEMINI_API_KEY`. New required keys should be discussed in the PR.

### Cross-module discipline (API only)

A module **must not** import another module's `domain/` or `internal/` layer. Two exceptions:
1. Any module may import `get_current_user`, `require_role`, `Role`, `User` from `auth`.
2. A service may import a foreign repository directly for read-only data composition within the same session — never call another module's service methods.

Cross-module **composition** lives in `src/core/` (see `inference_detector.py`, `extension_pipeline_submitter.py`). If you find yourself wanting to import across modules, write an adapter in `src/core/` and wire it onto `app.state` in `lifespan` instead.

## What not to add

- **Comments that restate code.** The API and dashboard both keep comments tight — only add one when the *why* is non-obvious (a hidden constraint, a workaround, a contract reference).
- **A test framework on a casual PR.** Neither repo has one configured; do not introduce pytest/jest as a side-effect of an unrelated change. If you want to add testing infrastructure, open a dedicated PR for it.
- **Linters / formatters on a casual PR.** Same rule.
- **A new env var with no default.** Required env vars block boot — discuss in the PR before adding.
- **Backwards-compatibility shims.** This system is not yet at the point where the API contract is frozen; if you change a response shape, change the dashboard at the same time rather than dual-supporting both.
